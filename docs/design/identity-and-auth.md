## 1. 三种角色的归属

```
平台管理员（我方运维）      tenant_id = NULL      不属于任何业务租户
     │
     ├── 租户 A（福州水务集团）── 租户管理员 老张 ── 操作员 / 只读
     └── 租户 B（闽运物流）  ── 租户管理员 ……
```

**平台管理员不属于任何业务租户**（D23）。他是系统维护者——我方开发运维，或客户侧拥有全节点最高权限的那个人。`users.tenant_id` 因此改为可空，`NULL` 即平台级用户。

这直接要求删除迁移中硬编码的 `default` 租户（`00000000-…-0001`）。该行目前身兼三职：平台管理员的归属、旧设备 `tenant_id` 回填、组织树同级唯一索引的哨兵值——三者都要各自解耦。

## 2. 租户生命周期

### 2.1 开通（D30）

建租户与建首个管理员是**同一个事务**：

```
POST /api/v1/tenants
  ├── 创建租户
  ├── 创建租户根节点（org_units，名称默认取租户名）  ← permission-model.md D11
  ├── 按所选套餐填充 tenant_modules                  ← permission-model.md D39
  └── 创建首个租户管理员
        · 用户名、初始密码：表单预填、允许修改
        · 角色：内置「租户管理员」
        · 管辖范围：租户根节点
        · 邮箱：必填
```

- **用户名与密码预填、可改**：纯自动生成的话，平台管理员还得从某处把密码抄给客户；纯手填又多一道功夫。
- **首个管理员的邮箱必填**（修订 D26）：他是这个租户唯一的兜底人，没有邮箱意味着将来忘记密码只能找平台方。
- 「租户建完却没有人能登录」是无效状态，不允许存在。

### 2.2 停用（D35）

**停用 = 该租户全部功能停用**，等同于欠费停机：开通模块视为空集，全部用户立即无法登录，已签发 token 立即失效。

- 立即生效，不设宽限期——宽限期是商务侧在按下停用之前的事。
- **需联动 Access 侧**：该租户设备的 SIP 注册要在 Kamailio 一并禁用，恢复时重新下发。这走已有的 outbox 通路，但**不是一条 `UPDATE` 能完成的**，实施清单里须单列。

### 2.3 删除（D35）

- **无需先停用**，可直接删除。
- 删除时要求**手动输入租户全名**二次确认。
- 级联删除：组织树、设备、通道、用户、角色、`tenant_modules`。
- **审计**：该租户内部的审计记录随之删除；但「平台管理员于某时删除了租户 X」这一条属于**平台级审计，保留**——否则删租户会成为销毁证据的手段。

## 3. 身份标识与登录

### 3.1 唯一性作用域（D40）

| 标识 | 唯一性 | 可否直接登录 |
|---|---|---|
| 用户名 | **租户内唯一**（保持现状，零 schema 改动） | 可，但可能需要消歧 |
| 邮箱 | **全局唯一**（整个节点内） | 可，直接定位 |
| 手机号 | **全局唯一** | 可，直接定位 |

邮箱与手机均**可以不填**（D26），仅租户首个管理员的邮箱必填。三者都不填的账号只能用用户名 + 密码登录，且**无法自助找回密码**——建账号时界面须把这个后果讲清楚。

### 3.2 登录时如何定位租户

登录框只有「账号 + 密码」两栏，**默认不问租户；撞名了才问**：

```
按账号查全库
├── 输入含 @ 或为 11 位纯数字 → 邮箱 / 手机，全局唯一，命中 ≤ 1 → 直接登录
├── 用户名命中 1 个                                          → 直接登录
├── 用户名命中 0 个                                          → 凭据错误（不区分原因）
└── 用户名命中 ≥ 2 个 → 追加要求输入「租户代码」
                        （不返回候选租户列表，减少信息泄漏）
```

**租户代码**：建租户时分配的短标识（如 `fzsw`），平台管理员可指定、可修改。绝大多数节点只有 1–3 个租户，这一步永远不会触发。

平台管理员 `tenant_id = NULL`，同在这个查询里，天然可登录，不需要任何特例。

> **设计依据（2026-08-28 联网调研）**：钉钉、企业微信、飞书三家均把 `userid` 定义为**企业内唯一**，无一采用全局唯一。钉钉在「企业账号」场景（组织给员工开账号，与本项目场景一致）明确要求**登录时输入组织代码**，系统默认分配 8 位随机码、管理员可申请个性化码。飞书则分两层：手机号注册生成全局 `lark_id`，而 `user_id` 是企业内身份，**同一用户在企业 A 和企业 B 的 `user_id` 不同**，且一个用户可同时加入多个企业、数据层面相互隔离。
>
> 曾一度决定「三种标识全部全局唯一、彻底去掉租户栏」，被上述证据推翻：强制用户名全局唯一等于把租户隔离捅穿到命名空间上，第 N 个租户想用 `admin` 就会撞车，**而撞车本身即泄漏了「别的租户有个叫 admin 的人」**。

### 3.3 登录方式（D22）

| 方式 | 前提 |
|---|---|
| 账号（用户名 / 邮箱 / 手机）+ 密码 | 始终可用 |
| 邮箱验证码 | 账号填了邮箱，且节点配置了 SMTP |
| 短信验证码 | 账号填了手机，且节点配置了短信网关（**当前仅预留接口，不接具体服务商**） |

**一个人同时属于两个租户 —— 不支持**：开两个账号、用不同邮箱。飞书那种「一个全局身份加入多个企业」的两层模型在视频监控场景没有需求（不会有人同时是水务集团和物流公司的员工），为它做账号选择器是过度设计。若将来需要，按飞书模型追加一层全局身份即可，现有结构不阻碍。

### 3.4 外发通道由部署形态决定（D24）

架构基线要求节点可部署在客户内网并断网自治。**内网部署下 SMTP 与短信网关通常不通**，因此：

- 节点配置了 SMTP → 出现「邮箱验证码登录」入口与「忘记密码」链接；
- 未配置 → 登录页只显示密码登录，密码重置只能由管理员执行；
- 短信同理，且当前只预留接口。

**即使当前是内网部署，建账号时也要允许填写邮箱和手机**——客户日后开通公网，改配置即生效，不必回头补录几百个账号。

## 4. 密码

### 4.1 强度规则（D25）

- 长度 **≥ 8**，< 256 字节；
- 至少满足「英文 / 数字 / 符号」**三类中的两类**。

> 曾考虑「≥6 且三类必须齐全」，改为 8+2：6 位强制三类的实际搜索空间小于 8 位两类，且强制符号最常见的后果是用户把密码写在便利贴上。配合 §5 的登录限流，8+2 足够。

### 4.2 重置路径

| 谁 | 怎么重置 |
|---|---|
| 普通用户 | 自助（邮箱/短信验证码，需外发通道）或找租户管理员 |
| 租户管理员 | 自助（首个管理员邮箱必填）或找平台管理员 |
| **平台管理员** | **运维侧命令行**：`node-app admin reset-password --username <name>`，直连数据库改哈希 |

平台管理员没有上级，内网下也发不出邮件。命令行重置要求执行者能登上服务器——这本来就是平台管理员的权限边界，不降低安全性。

**明确不做**：应急后门账号、万能恢复码。那种东西一旦泄漏即整节点失守，且会永远躺在代码里。

### 4.3 不做首次强制改密

由平台管理员/租户管理员设定初始密码后直接可用。但**必须提供自助改密接口**——当前系统完全没有，用户自己改不了密码，这条链是断的。

## 5. 会话与失效

### 5.1 停用即失效（D32）

账号被停用或其租户被停用后，**已签发的 token 立即失效**。

实现方式：认证中间件本就要读库取角色，顺带检查 `users.status` 与 `tenants.status`，任一非 `active` 即返回 **401**（不是 403——前端据此跳登录页）。**不引入 token 黑名单**。

> 当前实现完全没有这一步：`users.status` 只在登录时校验一次，停用后旧 token 可继续全权工作至过期（默认 24h，可配至 30d）。详见 [`permission-model.md`](permission-model.md) §9.1 缺陷 B（不变量 I2）。

### 5.2 权限变更即时生效

角色、范围、套餐的变更下一次请求即生效——中间件每次请求读库，无缓存。

**但当前有一处违反**：`visibleOrgIDs` 用 JWT 的 `rol` claim 判断平台管理员短路，而非实时角色，导致降级后的用户凭旧 token 仍拥有全租户可见性。这是提权缺陷，见 `permission-model.md` §9.1 缺陷 A（不变量 I1）。

### 5.3 限流（D27）

| 计数维度 | 阈值 | 动作 |
|---|---|---|
| 账号 + IP 组合 | 15 分钟内 5 次失败 | 对该组合退避 |
| 单 IP 跨多账号 | 单独计数 | 防撞库 |

**不锁定账号**：锁定策略在有真人攻击时会变成拒绝服务工具——任何人故意输错某人的密码 5 次就能把他锁在门外。

## 6. 合规说明

《网络安全法》第二十四条的实名要求，适用范围是「为用户办理网络接入、域名注册服务，办理固定电话、移动电话等入网手续，或者为用户提供**信息发布、即时通讯等服务**」。

本平台是私有化部署的企业内部管理系统，不属于上述任一类，**该条不直接适用**，无需为其设计实名认证流程。

## 7. 决策记录

> 编号与 [`permission-model.md`](permission-model.md) 共用一个序列（接续 `identity-scope-refactor.md` 的 D1–D10）。

- **D22 账号有三种标识**（用户名 / 邮箱 / 手机），四种登录方式（账号+密码、邮箱验证码、短信验证码〔预留〕）。
- **D23 平台管理员不属于任何业务租户**：`users.tenant_id` 可空，NULL = 平台级；删除硬编码的 `default` 租户。
- **D24 外发通道由部署形态决定**：配了 SMTP / 短信网关才启用验证码登录与自助重置；内网部署即不支持。建账号时仍允许填写邮箱手机。
- **D25 密码 ≥8 位、< 256，至少满足英文 / 数字 / 符号三类中的两类。**
- **D26 邮箱、手机均可不填**；填了即可用于登录。三者皆空的账号只能用户名+密码登录且无法自助找回。**例外：租户首个管理员的邮箱必填。**
- **D27 登录失败限流**按「账号 + IP」组合退避（15 分钟 5 次），并对「单 IP 跨多账号」单独计数；**不锁定账号**。
- **D30 建租户与建首个管理员同事务**：用户名与初始密码预填可改，角色为内置租户管理员，范围为租户根节点。
- **D32 停用账号或停用其租户后，已签发 token 立即失效**（中间件顺带检查状态，返回 401）；不引入 token 黑名单。
- **D35 停用租户 = 全部功能停用**（含 Access 侧禁用设备注册）；**删除租户无需先停用**，手输全名确认后级联删除，租户内审计随删、平台级删除记录保留。
- **D40 登录默认不问租户，撞名才问**：用户名租户内唯一，邮箱手机全局唯一；用户名命中多个时才要求输入租户代码，且不返回候选列表。
- **不做**：首次登录强制改密（D25 附）、应急后门账号 / 万能恢复码（§4.2）、一个人跨租户共享身份（§3.3）。
