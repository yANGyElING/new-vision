## 0. 三类权限

平台里「权限」是三件互相独立的事，任何一次请求都要依次过这三关：

| | 回答的问题 | 由什么决定 |
|---|---|---|
| **租户套餐**（开通） | 这个租户**买了**哪些模块 | `tenant_modules`（§4） |
| **功能权限**（菜单） | 你能**做**什么 | 用户的角色所含的权限点集合 |
| **数据权限**（范围） | 你能对**哪些**对象做 | 用户的管辖范围（组织树上的节点集合） |

三者正交。一个「只读」角色的人，范围可以是全公司；一个「租户管理员」的范围也可以只有一个泵站；而无论角色多大，没开通的模块一律不可用。

判定链（以「老张下载某段录像」为例）：

```
请求 → 认证
  ├─ 租户套餐：水务集团开通「录像」模块了吗？
  │     ↓ 否 → 菜单里根本没有这个入口（前端），后端 403
  ├─ 功能权限：老张的角色含 record:download 吗？
  │     ↓ 否 → 403
  ├─ 数据权限：这段录像所属通道，在老张的范围内吗？
  │     ↓ 否 → 404（不暴露存在性）
  └─ 执行
```

推论：老张给别人建角色时，勾选框里能出现的权限点 =
**他自己拥有的 ∩ 本租户已开通的 ∩ 标记为租户级的**（分别对应 D14、D39、D19）。

> 账号本身怎么来、怎么登录、密码与会话如何管理，见 [`identity-and-auth.md`](identity-and-auth.md)。

## 2. 数据权限

### 2.1 租户根节点（D11）

每个租户在**创建租户的同一事务里**自动生成一个根节点，默认名为租户名。

- 根节点**不可删除、不可移动**，可改名。
- 一个租户**有且只有一个**根：数据库层用 `parent_id IS NULL` 的部分唯一索引强制。
- `devices.org_unit_id` **非空**。未归类的设备就挂在根节点上——「待归类」不再是特殊状态，而是「归属 = 根节点」这个普通值。
- 因此 `users.all_orgs` 标记**取消**：「全公司」= 管辖范围勾中根节点。

> 这一条推翻 `identity-scope-refactor.md` 的 D4（不播种默认根）与 D5（all_orgs 显式标记）。
> D4 当时否掉的是**旧的那种根**：全局一棵树（`regions` 无 tenant_id）+ 写死在代码里的魔法 UUID。
> 每租户一棵、建租户时顺手创建的根，这两个毛病都没有。
> D5 的理由是「全选顶层节点会漂移」——有了强制唯一的根之后，勾根不会漂移，标记因此冗余。

**它删掉的东西**：`org_unit_id IS NULL` 这条分支。上一轮 code review 的 CRITICAL 缺陷（平台管理员设备列表恒为空）正出自这条分支，一处写错连带炸了 4 个调用点。分支消失，这类缺陷随之消失。

### 2.2 范围语义：唯一一条规则（D16）

> **勾一个组织节点 = 授予该节点，以及它现在和将来的全部后代。**

没有第二种语义，没有「是否含后代」的开关。

因此「勾 A」与「勾 A 的全部子节点」是**两种都合法、且不等价**的表达：

```
鼓楼片区 (A)
├── 五凤泵站   (A1)
└── 洪山桥泵站 (A2) … A10
```

| 选法 | 现在 | 新增兄弟节点 A11 | 新增孙节点（A1 下） |
|---|---|---|---|
| 勾 **A** | A 直属设备 + 全部子节点 | ✅ 自动获得 | ✅ 自动获得 |
| 勾 **A1…A10** | 仅 10 个子节点，**不含 A 直属设备** | ❌ 不获得 | ✅ 自动获得 |

**授权永远沿着所勾节点向下生长，但不会横向长到兄弟节点。**

#### 不做兄弟上卷

曾考虑：子节点被全选时自动折叠为父节点（A1…A10 → A）。**否决**，两个理由：

1. **它多授权**。多出 A 直属的待归类设备 + 未来的 A11——而「就这 10 个、以后新增的不给」是真实且合理的授权意图，一旦上卷就永远表达不出来。
2. **它省不到性能**。展开成本是 O(结果子树大小)，不是 O(种子数)；从 A1…A10 出发与从 A 出发遍历的子树几乎一样大。

降级为**被动提示**：子节点全选而父未选时，在父节点旁显示一行灰字「该组织下 N 个子组织已全选，改为勾选本节点可自动包含以后新增的子组织 [改为勾选]」。不弹模态框、不默认执行、不阻塞保存——授权界面的任何默认动作都应倾向于授得更少。

#### 祖先吸收（保留）

范围集合中若同时存在祖先与后代（如 `{A, A1}`），保存时只留祖先。

- 界面上产生不了这种组合：勾中 A 后，其全部后代置灰显示为「已包含」，不可单独勾选或取消。
- 因此吸收只是 **API 层的归一化兜底**，防止绕过界面直接调接口。
- 它的真正价值在性能：保证展开时**种子互不重叠**，见 2.3。
- 已知副作用：若 A1 日后被移出 A 的子树，该用户对 A1 的授权随之消失。接受——存最小集合是对「当时授了什么」的诚实表达，且移动本身受 D15 的范围约束。

### 2.3 范围解析与性能

```sql
WITH RECURSIVE subtree AS (
    SELECT id FROM org_units WHERE id = ANY($1)
    UNION ALL
    SELECT c.id FROM org_units c JOIN subtree s ON c.parent_id = s.id
)
SELECT id FROM subtree;
```

**`UNION ALL` 的正确性前提是种子互不重叠**——即 2.2 的祖先吸收必须先做。否则范围里同时存在 `{A, A1}` 时，A1 那棵子树会被**完整遍历两遍**，且结果集含重复 ID。嵌套越深、冗余越多，重复工作量翻得越厉害。这是「勾太多节点会不会慢」的真实来源，而非种子数量。

实测量级估算：

| 树规模 | 全树展开 | 占一次设备列表请求 |
|---|---|---|
| 200 节点 | ~0.3 ms | < 3% |
| 2000 节点 | ~2 ms | ~15% |
| 20000 节点 | ~20 ms | 需要缓存 |

最坏情况（种子极多且互不重叠）= 遍历全树一次。**当前规模不值得任何优化。** 真要优化，顺序是：

1. 祖先吸收（现在就做，同时是正确性前提）；
2. 按「用户 + 组织树版本号」缓存展开结果，树变更或范围变更时失效（节点上千时）；
3. 物化路径（每节点存 `/根/鼓楼片区/五凤泵站/`，子树判定退化为前缀匹配，完全不用递归）。代价是移动节点需更新整棵子树的路径（节点上万时）。

### 2.4 可见性规则

| 条件 | 可见设备 |
|---|---|
| 平台管理员（node_admin） | 全部租户，不做组织过滤 |
| 其他用户 | 各范围节点子树展开的并集内的设备 |
| 空范围 | 空集（默认拒绝） |

根节点非空保证了不存在「谁都看不见的设备」——最坏情况是它待在根上，被范围含根的人（通常是租户管理员）看见。

### 2.5 组织树本身也按范围限制（D15）

组织架构页显示的树，**从用户自己的范围节点开始**，范围之外的枝杈不显示（不是置灰，是不出现）。

小李（范围 = 鼓楼片区）看到的：

```
鼓楼片区
├── 五凤泵站
└── 洪山桥泵站
```

| 操作 | 小李 | 说明 |
|---|---|---|
| 在鼓楼片区下新增子节点 | ✅ | 父节点在范围内 |
| 给五凤泵站改名 | ✅ | |
| 把五凤泵站移到洪山桥泵站下 | ✅ | 起点与目标都在范围内 |
| 删除五凤泵站 | ✅ | 迁移目标选择器也只列范围内节点 |
| 给鼓楼片区改名 | ✅ | |
| **删除或移动鼓楼片区本身** | ❌ | 那是他的立足点；移动的目标父节点必然在范围外 |
| 操作台江片区 | ❌ | 不可见 |

**自洽的副产品**：若小李的范围是 A1…A10（10 个泵站，不含父节点），他看到 10 棵并排的树，可以在任一泵站下加子节点，但**无法新建与它们平级的 A11**——因为那需要以鼓楼片区为父，而鼓楼片区不在他范围内。权限与操作两头封死，无需额外规则。

### 2.6 删除组织单元（D12）

不直接删除，先弹迁移对话框：

```
删除「台江片区」

该组织下还有：
  · 1 个子组织（苍霞泵站）
  · 8 台设备

请选择它们移动到哪里：
  ┌────────────────────────────┐
  │ ○ 福州水务集团（全公司） ←默认│
  │ ○ 鼓楼片区                  │
  │ ○ 第一水厂                  │
  └────────────────────────────┘

          [取消]  [移动并删除]
```

- **默认预填父节点**——「撤掉片区、下级直接上挂」是最常见的意图。
- 子组织与设备**一起处理**：苍霞泵站整体搬迁，其下 8 台设备随之移动。
- **必须是后端单事务**：`DELETE /api/v1/org-units/{id}?move_to={target}`，一个事务内改设备归属、改子节点父级、删节点。拆成前端多次请求会在中途失败时留下「设备已迁走但组织还在」的半成品状态——`identity-scope-refactor` 的 review Finding 4 就是同类问题（改名与移动分处两个事务）。
- 目标节点下若已存在同名子组织，在**弹窗内当场拦截**，不能等提交才报错。
- 目标选择器受 2.5 约束：只列操作者范围内的节点。

### 2.7 新增组织节点时提示影响面（D17）

老张新建「杨桥泵站」时，界面提示：

> 该组织将自动被 2 个用户看到（老张、小周），因为他们的范围包含上级「鼓楼片区」。

在**后果发生的那一刻**告知，比要求管理员在授权时预判未来更有效。这也是「完全冻结式授权」（授权不含未来子孙）被否决的替代方案——冻结会让授权变成过期快照，树一变动就悄悄产生无人管辖的设备。

### 2.8 设备与通道：两个授权对象（D28 / D36）

一台 NVR 挂 32 路摄像头。**设备和通道都可以挂组织树**，各管各的事：

| 对象 | 挂树的含义 | 服务于谁 |
|---|---|---|
| **设备**（NVR / IPC） | 谁能**管理**它：改参数、启停、删除、看在线状态 | 运维口 |
| **通道**（摄像头画面） | 谁能**看到并调阅**这路画面 | 业务口 |

这个划分和 D29（「看得到」与「能调画面」是两个权限）天然对齐：设备归属对应管理权，通道归属对应查看权。

```sql
channels.org_unit_id UUID NULL          -- NULL = 跟随所属设备（默认）

-- 判定一路画面归谁：
COALESCE(c.org_unit_id, d.org_unit_id)
```

- **默认永远是 NULL**：Catalog 同步上报的 32 路自动跟随设备，日常零操作；设备换组织时，所有跟随的通道自动跟着走，无需任何维护代码。
- 需要拆开时（同一台 NVR 上，周界归安保部、工艺设备归生产部——NVR 装在哪由布线决定，画面归谁管由组织决定），才单独覆盖某几路。
- **两者的可见性独立计算**：能看某路画面 ≠ 能管那台 NVR，反之亦然。
- UI 初期**不提供**单独设置通道归属的入口，等有实际需求再开。
- 受 D14/D15 约束：把某路通道划到某个组织，目标节点必须在操作者自己的范围内。

## 3. 功能权限

### 3.1 用户管理下放给租户管理员（D13）

租户管理员**可以自己开账号**。不下放的话，水务集团每加一个门卫、每次轮岗、每次离职停号都要联系我方运维——运维量不可接受，客户也无法接受「自己公司的账号自己管不了」。

> 讨论过程中曾一度决定「不下放」（理由是账号线全部握在平台侧最安全），随即因运维负担推翻。记录于此以免重复讨论。

下放的前提是**先拆权限点**：当前后端只有一个 `identity:manage`，同时管着两组接口——

```
POST/GET/PATCH  /api/v1/tenants     ← 建租户、改租户
POST/GET/PATCH  /api/v1/users       ← 建用户、改用户
DELETE          /api/v1/users/{id}
```

直接下放会连带把「新建租户」的能力交出去。必须拆成：

| 权限点 | 管什么 | 给谁 |
|---|---|---|
| `tenant:manage` | 建/改租户 | **仅平台管理员，永不下放** |
| `user:manage` | 建/改本租户用户 | 平台管理员 + 租户管理员 |

这不是重构洁癖，这个拆分本身就是下放的安全边界。

### 3.2 授权子集规则（D14）

> **你能授出的权限集合，必须是你自己拥有的权限集合的子集。**

老张拥有 `{device:*, org_unit:manage, user:manage}`，那么他建角色时勾选框里就只有这些；租户管理、节点运维、SIP 测试台**在界面上不存在**，后端再校验一次兜底。

这一条同时兑现三件事：

- **数据权限限本租户范围** → 组织树只显示自己那一支（复用 2.5 的同一套过滤）；
- **菜单权限封顶** → 授权人自身的集合就是天花板，捏不出超过自己的角色；
- **授权不越权** → 子集校验递归自洽：小李若也是自定义角色，他再往下授时天花板换成他自己的集合，规则不用改。

**它取代了「不能授出比自己高的角色」**。一旦租户能自定义角色，角色之间就没有统一次序，偏序规则失效；而子集规则更本质，且自动涵盖「造不出平台管理员」（平台级权限点不在租户管理员集合内）。

配套的三条边角：

| 场景 | 规则 |
|---|---|
| 改自己 | 不能修改自己的角色与管辖范围；改密码、改昵称可以 |
| 用户列表可见性 | 只能看到**管辖范围完全落在自己范围内**的用户。老张范围为根，不在小李范围内 → 小李的用户列表里没有老张 |
| 范围被上级缩小后 | 小李从「鼓楼片区」缩到「五凤泵站」后，他此前建的「洪山桥泵站」账号超出其范围，他不再可见可改（老张仍可管）。无需特殊处理，但需知晓 |

### 3.3 权限点分级（D19）

子集规则单独用有一个洞：平台管理员拥有**全部**权限点，按子集规则他可以给租户捏一个含 `tenant:manage` 的角色，租户拿到后即可建租户。

因此权限点本身必须打标：

| 级别 | 权限点 | 可否出现在租户角色中 |
|---|---|---|
| 租户级 | 设备（增删改查/启停）、组织架构管理、用户管理 | ✅ |
| 平台级 | 租户管理、节点运维、Access 控制台、SIP 测试台 | ❌ **永不** |

**两道闸正交**：子集规则管「不超过授权人」，分级规则管「租户角色里不许含平台能力」。缺任何一道都有洞。

### 3.4 角色从编译期常量变为数据（D18）

当前 `rolePermissions` 是 `internal/authz/model.go` 里的 Go map。支持租户自定义后必须入库：

```sql
roles (
    id        UUID PRIMARY KEY,
    tenant_id UUID NULL,          -- NULL = 内置角色；非空 = 该租户自定义
    name      VARCHAR(255) NOT NULL,
    is_builtin BOOLEAN NOT NULL DEFAULT FALSE
);
role_permissions (role_id UUID, obj VARCHAR, act VARCHAR);
```

- 内置四角色（平台管理员 / 租户管理员 / 操作员 / 只读）以 `tenant_id IS NULL` 播种，**不可编辑、不可删除**；租户可直接使用，也可复制一份再改。
- **权限点清单仍由代码定义**，不入库、不可扩展。租户能自由组合权限点，但发明不了新权限点——这是整套安全模型的地基。
- 这一条推翻 `identity-scope-refactor.md` 的 D7（角色矩阵是编译期常量、直接查表）。去 Casbin 的决定保留：仍然不需要规则引擎，只是查表的数据源从 Go map 变成数据库表。

### 3.5 角色的生命周期（D20）

- **单选**。一个账号只绑一个角色。多角色叠加会让子集校验与事后排查都急剧复杂化。
- **改角色即时生效**：中间件本就每次请求读库、无缓存。但界面上修改角色时须提示「将影响 N 个账号」。
- **删角色**沿用 2.6 的模式：提示「还有 N 个账号在用」，弹选择器让操作者选替代角色，后端单事务完成。

### 3.6 权限点完整清单

权限点由代码定义，不入库、不可扩展；租户能自由组合，但发明不了新权限点。这是整套安全模型的地基。

**平台级 —— 永不出现在租户角色中（D19）**

| 模块 | 权限点 |
|---|---|
| 租户管理 | `tenant:view` `tenant:create` `tenant:update` `tenant:disable` `tenant:delete` |
| 节点运维 | `access:view` `access:events` `access:ack` |
| SIP 测试台 | `test:sip:register` `test:sip:keepalive` `test:sip:unregister` |
| 跨租户审计 | `audit:view:all` |

**租户级 · 基础能力 —— 不可关闭**

| 模块 | 权限点 | 范围锚点 |
|---|---|---|
| 设备管理 | `device:view` `device:create` `device:update` `device:enable` `device:delete` | `devices.org_unit_id` |
| | `channel:view` `channel:update`（改名、调归属） | `COALESCE(channels.org_unit_id, devices.org_unit_id)` |
| 组织架构 | `org_unit:view` `org_unit:create` `org_unit:update` `org_unit:move` `org_unit:delete` | 自己范围那一支子树 |
| 用户与角色 | `user:view` `user:create` `user:update` `user:delete` `user:reset_password` | 目标用户范围 ⊆ 自己范围 |
| | `role:view` `role:create` `role:update` `role:delete` | 本租户 |

> 组织架构与用户管理**不可作为套餐项关闭**：关掉用户管理，D13（把开账号的权力下放给租户管理员）就失效，租户又得回来找平台方。

**租户级 · 可选模块 —— 按套餐开关（D39）**

| 模块 | 权限点 | 范围锚点 |
|---|---|---|
| 实时视频 | `stream:play` | 通道 |
| 云台控制 | `ptz:control` `ptz:preset` | 通道 |
| 录像 | `record:view` `record:playback` `record:download` | 通道 |
| 告警 | `alarm:view` `alarm:ack` `alarm:config` | 通道 / 设备 |
| 审计 | `audit:view` | 本租户 |

「改自己的密码和资料」不是权限点，是所有登录用户天生具备的能力。

## 4. 租户功能开关（套餐）

「这个租户买了什么」是判定链的第一关。**唯一事实来源是租户已开通的模块集合**：

```
tenant_modules（该租户实际开通了哪些模块）   ← 唯一事实
      ↑
   套餐只是往里填的模板：Basic / Pro / Ultra
```

- 建租户时选套餐 → 一键填充模块集合；
- 之后可单独加减某个模块（客户单买一个云台）；
- **套餐本身不存储在租户身上**，存的永远是模块集合。

这样「按套餐卖」和「自定义开关」是同一套数据的两个入口，不会出现「套餐写着 Pro，但模块被单独改过」这类对不上的状态。**与内置角色是同一个模式**（D34：预设直接可用 + 可复制修改）——整套系统里「预设 + 可调」只有一种做法。

**降级的处理**：租户从 Ultra 降到 Pro，角色里超出套餐的权限点**保留但不生效**（第一关直接挡掉），升级回来自动恢复。不做清理——清理了升级还得重配，且会误删客户自定义的角色。

**停用租户 = 开通模块为空集**，即 §5 之外一切皆不可用（D35，详见 [`identity-and-auth.md`](identity-and-auth.md)）。

## 5. 审计

**记录永远开启，查看按套餐售卖（D37）。**

记录是平台的基础能力，不可关闭——否则出了事平台方自己也无从排查。可售卖的是「让租户自己查」这个能力。

**可见性（D21）**：

| 谁 | 能查什么 |
|---|---|
| 平台管理员 | 全部租户（`audit:view:all`） |
| 租户管理员（且租户开通了审计模块） | 本租户，且只看得到**管辖范围落在自己范围内**的操作 |
| 其他角色 | 不可查 |

**记录范围（D33）**：只记录**授权类与结构类写操作**，不记录读操作——

- 用户：创建 / 修改 / 删除 / 重置密码 / 停用
- 角色与范围：角色增删改、用户范围变更
- 组织：新建 / 改名 / 移动 / 删除（含设备迁移目标）
- 设备与通道：创建 / 修改 / 归属变更 / 启停 / 删除
- 租户：创建 / 停用 / 删除 / 套餐变更
- 登录：成功与失败
- **授权拒绝（403）**

理由：这些操作事后**无法从数据反推**（改完范围看不出改之前是什么），且是客户合规必问项；只记写操作，数据量很小。

> 审计表 `audit_logs` 与写入器已经存在（`migrations/000004_auth.up.sql:57-70`、`internal/audit/audit.go`）。缺的是：403 拒绝未记录、`Result` 被硬编码为 `success`、`IPAddr` 从未赋值、以及没有任何读取接口和页面。见 §9.1 缺陷 G。

## 6. 不变量与强制点

前面各节描述的是**行为**；这一节列出必须永远成立的**不变量**，以及每条由哪一层强制。

§9.1 里的每一条缺陷，都是某条不变量当初没有被明确写下来、于是也没有地方强制它。修复的目标不是打补丁，而是把缺失的那条约束补上。

| # | 不变量 | 强制在哪一层 | 对应缺陷 |
|---|---|---|---|
| **I1** | 所有权限判定使用**数据库实时状态**，**绝不**使用 JWT 载荷里的角色或范围 | 认证中间件（唯一入口） | A |
| **I2** | 账号或其租户非 `active` 时，已签发的 token 立即失效，返回 **401** | 认证中间件 | B |
| **I3** | 任何指向 `org_units` 的外键，其所在行的租户必须与该组织单元的租户一致 | **数据库复合外键** | D |
| **I4** | 除登录外，所有路由注册在认证守卫内；**权限分派不得先于认证** | 路由注册 | E |
| **I5** | 认证中间件按 user id **单条查询**，不得加载用户列表 | 认证中间件 | C |
| **I6** | 每个租户有且只有一个根节点（`parent_id IS NULL`） | 部分唯一索引 | 新增（D11） |
| **I7** | `devices.org_unit_id` 非空——不存在无归属的设备 | `NOT NULL` | 新增（D11） |
| **I8** | 授权拒绝（403）必须落审计，`Result` 为真实值，`IPAddr` 必须赋值 | 认证中间件 | G |
| **I9** | 权限点所属模块未被租户开通时，后端一律拒绝——**前端不显示菜单不构成防护** | 认证中间件 | 新增（D39） |
| **I10** | 平台管理员的「当前租户」由**统一的请求上下文**承载，不由各接口自行约定 | 认证中间件 | 新增（D31） |

### 6.1 I3：把跨租户一致性交给数据库，而不是代码

`identity-scope-refactor.md` §1.3 当初的决定是「由应用层校验，DB 层不强行跨表复合外键」。**这个决定被本文推翻**——结果就是缺陷 D：三处写入路径中没有一处做了校验，唯一的守卫还在特权分支上无条件放行。

约束交给数据库，就没有「某个新写的 handler 忘了校验」这种可能：

```sql
-- 前提：让 org_units 可被复合外键引用
ALTER TABLE org_units
  ADD CONSTRAINT org_units_id_tenant_uniq UNIQUE (id, tenant_id);

-- 设备的组织归属必须与设备同租户
ALTER TABLE devices
  ADD CONSTRAINT devices_org_same_tenant
  FOREIGN KEY (org_unit_id, tenant_id) REFERENCES org_units (id, tenant_id);

-- 通道、用户管辖范围同理（各自冗余存 tenant_id 后加同形状的复合外键）
```

**为什么保留 `devices.tenant_id` 这个「冗余」列**：`org_unit_id` 非空之后租户确实可以推导出来，但设备列表是热路径，每次都 join `org_units` 才能按租户过滤不划算。保留冗余列 + 复合外键 = 既快又不可能不一致。**冗余本身不是问题，无人强制的冗余才是。**

### 6.2 I9：套餐检查必须在后端

判定链第一关（租户是否开通该模块）**不能只靠前端隐藏菜单**。中间件在校验权限点时，同时查这个权限点所属模块是否在 `tenant_modules` 中；不在即 403。

这也是为什么 §3.6 的权限点清单要按模块分组，且**模块分组与套餐开关同源**（D39）——两套清单一定会漂移，漂移之后「角色里有、套餐里没有」就会变成谁也说不清的行为。

### 6.3 I10：平台管理员的租户上下文

当前实现是分裂的：`/org-units` 和 `/users` 认 `?tenant_id=` 查询参数，而 `/devices` 只认 JWT 里的 `tid` 且不可覆盖。后果是平台管理员**能管任意租户的用户和组织，却只能看到自己所属租户的设备**——D31 的租户切换器在现状下根本无处落脚。

统一为：**`X-Tenant-Id` 请求头**承载当前租户上下文。

- 平台管理员（`tenant_id IS NULL`）：必须带该头，否则除「全部租户」允许的只读列表外一律拒绝；
- 普通用户：**忽略该头**，一律以 token 中的租户为准（带了也无效，不构成越权面）；
- 写操作一律要求已选定租户，不允许在「全部租户」上下文中执行。

## 7. 决策记录

> 编号接续 [`identity-scope-refactor.md`](identity-scope-refactor.md) 的 D1–D10。
> 账号与登录相关的 D22–D27、D30、D32、D35、D40 记录在 [`identity-and-auth.md`](identity-and-auth.md)。

- **D11 每租户自动根节点**：建租户同事务创建，不可删/不可移、可改名，每租户唯一（部分唯一索引强制）。`devices.org_unit_id` 改为非空，未归类设备挂根节点。**取消 `users.all_orgs`**，「全公司」= 勾中根节点。推翻 D4、D5。
- **D12 删除组织单元 = 提示 + 迁移目标选择 + 单事务**：默认预填父节点，子组织与设备一并迁移，同名冲突在弹窗内拦截。
- **D13 用户管理下放给租户管理员**：前提是先把 `identity:manage` 拆成 `tenant:manage`（永不下放）与 `user:manage`。
- **D14 授权子集规则**：能授出的权限集合 ⊆ 自己拥有的集合。取代「角色偏序」。附带：不能改自己的角色与范围；用户列表仅显示范围落在自己范围内的用户。
- **D15 组织树的查看与编辑按管辖范围限制**：范围外的节点不显示；不能删除或移动自己范围的根节点。
- **D16 范围语义唯一规则**：勾一个节点 = 该节点 + 全部后代（含未来）。不做兄弟上卷（只作被动提示）；祖先吸收作为 API 层归一化，同时是 `UNION ALL` 展开的正确性前提。
- **D17 新增组织节点时提示受影响用户**：告知哪些用户会因范围继承自动获得访问权。
- **D18 角色入库**：内置角色 `tenant_id IS NULL` 不可改；租户自定义角色 `tenant_id` 非空。权限点清单仍由代码定义、不可扩展。推翻 D7 的「编译期常量」部分，保留「不用规则引擎」。
- **D19 权限点分级**：租户级 / 平台级；平台级权限点永不出现在租户角色中。与 D14 正交，两道闸缺一不可。
- **D20 角色单选**；改角色即时生效并提示影响账号数；删角色需选替代角色，单事务完成。角色名同租户内唯一，且不得与内置角色重名。
- **D21 审计对管理员开放**：平台管理员看全部租户；租户管理员看本租户，且仅限管辖范围落在自己范围内的操作（需租户已开通审计模块）。
- **D28 设备与通道都可挂组织树**：设备归属 = 管理权锚点，通道归属 = 查看权锚点，两者独立计算。
- **D29「看得到」与「能调画面」分离**：媒体类权限点（播放 / 云台 / 录像查看 / 录像下载）独立于设备查看权，现在就进清单，不等功能落地。依据：架构基线 §9.3「区域管理员默认不拥有实时视频、PTZ、录像查看和下载权限」。
- **D31 平台管理员用顶部全局租户切换器**决定当前上下文；「全部租户」选项只在设备列表可用，写操作必须先选定租户。
- **D33 审计范围**：只记录授权类与结构类写操作 + 登录 + 403 拒绝，不记录读操作。
- **D34 内置角色直接可用、可复制修改**，本体不可编辑不可删。
- **D36 `channels.org_unit_id` 可空**，NULL = 跟随设备；解析用 `COALESCE`；UI 初期不提供单独入口。
- **D37 审计记录永远开启**（平台基础能力，不可关）；**查看审计**是可选模块，按套餐售卖。
- **D38 录像作为一个模块**，内含 `record:view` `record:playback` `record:download`；「给回放不给下载」由角色区分，不由套餐区分。
- **D39 套餐 = 模块集合的命名模板**：唯一事实是 `tenant_modules`；降级时超出套餐的权限点保留但不生效，升级自动恢复。
